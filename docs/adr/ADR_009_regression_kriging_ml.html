ADR-005 · Atlas Géotechnique
Régression kriging hybride ML et kriging stratifié par profondeur
Accepté 2026-03-30 Pipeline scientifique ML/ONNX Dépend ADR-004

Contexte

ADR-004 établit le kriging stratifié par domaine géologique. Ce document étend l'architecture sur deux axes :

  • La régression kriging (RK) combine une tendance ML avec une interpolation des résidus, produisant des cartes plus précises que le kriging ordinaire seul.
  • Le kriging par horizon de profondeur traite la variabilité verticale des sols, inexploitée dans le pipeline actuel.

Ces deux extensions sont interdépendantes et partagent la même infrastructure de features, de traçabilité et d'export ONNX.

Décision 1 — Régression kriging : architecture à trois niveaux

La régression kriging décompose la variable cible en deux composantes :

Z(s) = m(s) + ε(s)

où m(s) est la tendance déterministe estimée par ML (CatBoost), et ε(s) est le résidu spatial interpolé par kriging ordinaire. La prédiction finale est :

Ẑ_RK(s₀) = m̂(s₀) + ε̂(s₀)

Trois niveaux de pipeline officiels

Niveau 1 — Kriging ordinaire stratifié (ADR-004)
  → sortie : ip_kriging, vbs_kriging par domaine géologique
  → source_type = 'kriging'

Niveau 2 — Régression kriging hybride ML
  → features : élévation DSM, pente, indice TWI, domaine géologique/pédologique
  → modèle tendance : CatBoost (export ONNX)
  → résidus : kriging ordinaire sur Z(sᵢ) - m̂(sᵢ)
  → source_type = 'regression_kriging'

Niveau 3 — Inférence ML directe (atlas-api-infer)
  → fallback si résidus non convergents
  → source_type = 'ml_infer'

Décision 2 — Kriging par horizon de profondeur dynamique

Les paramètres géotechniques varient verticalement. Un kriging ignorant la profondeur mélange des horizons physiquement distincts, produisant des valeurs sans réalité physique.

Les horizons sont définis dynamiquement par analyse des percentiles de la distribution des depth_m disponibles par paramètre et par domaine, plutôt que par des seuils fixes.

Algorithme de calcul des horizons dynamiques

Pour chaque (paramètre, domaine_géologique) :
  1. Extraire la distribution des depth_m avec valeurs non nulles
  2. Si n_points < 15 → pas de stratification, kriging 2D uniquement
  3. Sinon : découper en quartiles Q1/Q2/Q3 de depth_m
     → Horizon H1 : depth_m ≤ Q1   (typiquement 0–0.5m Togo)
     → Horizon H2 : Q1 < depth_m ≤ Q2  (typiquement 0.5–1.5m)
     → Horizon H3 : Q2 < depth_m ≤ Q3  (typiquement 1.5–3m)
     → Horizon H4 : depth_m > Q3   (typiquement > 3m)
  4. Vérifier n_points ≥ 15 par horizon avant kriging
     → Sinon : fusionner avec horizon adjacent

Les seuils calculés sont stockés dans atlas.kriging_depth_horizons et tracés par run.

Table de stockage des horizons

CREATE TABLE atlas.kriging_depth_horizons (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id        uuid REFERENCES atlas.ai_model_registry(id),
  parameter_id  text NOT NULL,
  domain_code   text NOT NULL,
  horizon_label text NOT NULL,  -- 'H1','H2','H3','H4'
  depth_min_m   float NOT NULL,
  depth_max_m   float,          -- NULL = ouvert vers le bas
  n_points      int NOT NULL,
  created_at    timestamptz DEFAULT now()
);

Décision 3 — Feature store pour RK (extension ADR-004)

La régression kriging nécessite des features spatiales continues pour calculer la tendance m(s). Ces features doivent être pré-calculées et versionnées pour reproductibilité.

Features obligatoires par maille

-- Features DSM/topographiques (déjà partiellement en base)
elevation_m          -- depuis atlas.dsm_flat_cache
slope_deg            -- calculé via PostGIS ST_Slope ou précompilé
twi                  -- Topographic Wetness Index = ln(a / tan(β))
aspect_deg           -- exposition versant

-- Features contextuelles
domain_geologie      -- clé FK vers atlas.kriging_domains
domain_pedologie     -- clé FK vers atlas.kriging_domains
risque_gonflement    -- catégorie 1-4

-- Features de voisinage (optionnelles niveau 2)
n_sondages_5km       -- densité locale de mesures
dist_nearest_sondage_m  -- distance au plus proche point de support

Décision 4 — Critères de sélection automatique du niveau pipeline

function select_pipeline_level(parameter, domain, horizon):
  n = count_support_points(parameter, domain, horizon)

  if n >= 30:
    run_level_2_regression_kriging()   → source_type = 'regression_kriging'
  elif n >= 15:
    run_level_1_kriging_only()         → source_type = 'kriging'
  elif n >= 5:
    run_level_3_ml_infer()             → source_type = 'ml_infer'
  else:
    run_deterministic_fallback()       → source_type = 'deterministic'
    emit WARNING(f"{domain}/{horizon}: n={n}, fallback activé")

Ce choix est loggé dans atlas.ai_run_log avec le motif explicite — aucune sélection silencieuse.

Conséquences

Gains
  • Précision accrue sur zones à tendance géologique forte
  • Variabilité verticale capturée (fondations, pieux)
  • Résidus traçables et auditables
  • Comparaison kriging / RK / ML dans UI graphiques
Coûts
  • Complexité pipeline x2 (horizons × domaines)
  • Données insuffisantes actuellement pour H3/H4 AMESSEFE
  • TWI et slope nécessitent DEM haute résolution Togo
  • Temps de run pipeline : x5–x10 vs kriging simple
