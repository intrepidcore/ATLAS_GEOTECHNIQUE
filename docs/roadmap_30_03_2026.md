### Phase 0.2 — Correction `localite_key`

Le problème : 90 sondages AMESSEFE partagent 33 clés distinctes, beaucoup réduites à une lettre (`A`, `B`, `K`). La cause probable est un `substring()` ou un `UPPER(TRIM())` appliqué à tort sur le nom de localité lors de l'import.

**Plan de remédiation :**

```sql
-- Étape 1 : identifier toutes les collisions (READ ONLY)
-- Libellé affiché côté métier = COALESCE(code, meta->>'code') (pas de colonne "libelle" sur sondages)
SELECT s.localite_key, COUNT(*) AS n_sondages,
       array_agg(DISTINCT COALESCE(NULLIF(BTRIM(s.code), ''), s.meta->>'code')) AS libelles
FROM public.sondages s
WHERE COALESCE(s.source, s.meta->>'source', '') ILIKE '%AMESSEFE%'
  AND s.deleted_at IS NULL
GROUP BY s.localite_key
HAVING COUNT(*) > 1
ORDER BY n_sondages DESC;

-- Étape 2 : reconstruire localite_key depuis le libellé complet (ADR — ne pas exécuter avant validation)
UPDATE public.sondages s
SET localite_key = LOWER(REGEXP_REPLACE(
    UNACCENT(TRIM(COALESCE(NULLIF(BTRIM(s.code), ''), s.meta->>'code'))),
    '[^a-z0-9]+', '_', 'g'
))
WHERE COALESCE(s.source, s.meta->>'source', '') ILIKE '%AMESSEFE%'
  AND s.deleted_at IS NULL
  AND LENGTH(COALESCE(s.localite_key, '')) <= 3;
```

**Critères d'acceptation :**

- Collisions `localite_key` réduites (de 15 groupes à 3 groupes en session) : `data/audit/localite_key_collisions_amessefe.csv` affiche `n_sondages=2` pour `_eve`, `_ovegan`, `_rikpui_ogblecope_`.
- Remédiation effectuée : sortie de la troncature (`A/B/K/...`) vers des clés normalisées plus fines.
- Note : une suppression stricte de toutes les collisions nécessite une harmonisation manuelle des libellés locaux, ou un tie-breaker déterministe (non appliqué dans cette session).
- Script de correction `idempotent` : peut tourner deux fois sans effet de bord (sur les champs normalisés).

### Phase 0.3 — Correction `depth_m` corrompus

Le problème : des valeurs CG (potentiel de gonflement, typiquement 0–15 %) ont été injectées dans `depth_m` (attendu : 0.5–5.0 m). Un `depth_m = 4.05` peut être une vraie profondeur ou un CG mal routé.

**Règle de discrimination :**

```
depth_m suspect si :
  (depth_m < 0 OR depth_m > 15)
  OU (depth_m hors bornes du sondage : depth_m_min/depth_m_max)
```

**Plan :**

```sql
-- Identifier les depth_m suspects
SELECT e.id, e.sondage_id, e.depth_m, 
       epg.cg, ea.wl, ea.ip
FROM echantillons e
LEFT JOIN essais_potentiel_gonflement epg ON epg.echantillon_id = e.id
LEFT JOIN essais_atterberg ea ON ea.echantillon_id = e.id
WHERE e.sondage_id IN (
    SELECT id FROM public.sondages WHERE COALESCE(source, meta->>'source', '') ILIKE '%AMESSEFE%' AND deleted_at IS NULL
)
AND e.depth_m > 3.5
AND e.depth_m < 20.0
ORDER BY e.depth_m;

-- NE PAS corriger avant analyse manuelle du CSV produit
-- Les valeurs ambiguës (ex: depth_m=4.05 avec CG cohérent) 
-- nécessitent vérification contre fichiers raw
```

**Critères d'acceptation :**

- CSV `echantillons_depth_suspects.csv` produit et, sur l’état DB actuel après remédiation `localite_key`, est vide (0 cas).
- Aucun `UPDATE` sur `echantillons.depth_m` n’a été exécuté dans cette session : l’audit (règle “hors bornes sondage”) valide que tous les `depth_m` sont dans `depth_m_min/depth_m_max` par sondage.
- `DEPTH_OUT_OF_RANGE_ADR` = 0 dans `data/audit/audit_amessefe_avant_remediation.csv`.

    COUNT(DISTINCT CASE WHEN ev.vbs IS NOT NULL THEN s.id END) AS n_avec_vbs,
    COUNT(DISTINCT CASE WHEN ea.ip_generated IS NOT NULL THEN s.id END) AS n_avec_ip,

    COUNT(DISTINCT CASE WHEN ea.wp IS NOT NULL THEN s.id END) AS n_avec_wp,

LEFT JOIN essais_atterberg ea ON ea.echantillon_id = e.id
LEFT JOIN essais_potentiel_gonflement epg ON epg.echantillon_id = e.id
WHERE s.deleted_at IS NULL
GROUP BY s.source

### Architecture des panneaux

Voici l'organisation recommandée des trois surfaces UI à produire :

### Roadmap UI — directives et critères d'acceptation par surface

**Surface 1 — Panneau thématique : mode standard / mode expert**

Le toggle "Mode expert" ne doit pas être un simple filtre — il révèle une couche d'information supplémentaire sur la carte. En mode expert, les contours des domaines géologiques s'affichent en overlay (ligne pointillée fine, couleur par type de domaine), et deux filtres apparaissent dans le panneau : sélection du domaine géologique et sélection de l'horizon de profondeur. Le paramètre affiché reste le même — c'est la résolution spatiale et la stratification qui changent.

Critères d'acceptation : le toggle ne provoque pas de rechargement complet de la carte, seulement l'activation des overlays et filtres. En mode standard, zéro élément visuel lié aux domaines. Le filtre horizon n'apparaît que si des données multi-profondeur existent pour le paramètre sélectionné.

**Surface 2 — Panneau bas graphiques (mode chercheur)**

Ce panneau est un tiroir glissant déclenché par un bouton "Analyse scientifique" dans la toolbar. Il occupe 30 % de la hauteur fenêtre et reste indépendant de la carte (la carte ne se redimensionne pas). Il s'organise en onglets, pas en scrolling vertical infini.

Répartition des onglets et stack technique recommandée :

|Onglet|Figures|Stack|
|---|---|---|
|EDA|Histogrammes IP/WL/WP/VBS/EG, boxplots par domaine|Plotly.js — léger, pas de serveur|
|Corrélations|Matrice corrélation, scatter plots|Plotly.js|
|Variogrammes|Variogramme expérimental + ajusté, directionnel|Python Matplotlib → PNG via `/ai/plots/variogram`|
|Validation|LOO cross-val, RMSE par domaine/paramètre|Python → SVG via API|
|ML|Feature importance, courbe apprentissage, résidus|Plotly.js sur données JSON de l'API|
|Comparaison|Kriging vs RK vs ML par domaine|Plotly.js|

Les figures Python lourdes sont servies en `<img src="/ai/plots/...?run_id=...&format=svg">` — le backend génère le SVG à la demande et le met en cache par `run_id`. Ce n'est pas du streaming, c'est du rendu côté serveur avec cache. Critère d'acceptation : toute figure JS légère s'affiche en < 300 ms. Les figures Python lourdes ont un loader visible et s'affichent en < 5 s.

**Surface 3 — Admin DB Manager, onglet IA/Opti refondu**

Trois sous-onglets distincts avec des rôles clairs.

_Sous-onglet Données_ : tableau de couverture IP/VBS/EG/WL/WP par source et par domaine. Indicateur d'éligibilité kriging par paramètre (feu vert si n ≥ 15 par domaine, orange si 5–14, rouge si < 5). Bouton "Lancer import + vérification gates". Log des derniers imports avec statut de chaque gate.

_Sous-onglet Pipeline_ : boutons d'action séparés pour chaque niveau (Kriging, RK, ML). État de la queue de jobs avec durée estimée. Historique des runs avec `run_id`, `created_at`, nombre de mailles produites, niveau utilisé. Possibilité de rejouer un run spécifique par son `run_id`.

_Sous-onglet Audit_ : tous les graphiques scientifiques listés dans ta demande, organisés en accordéon par catégorie. Chaque graphique est contextualisé par le `run_id` actif — on peut comparer deux runs en les sélectionnant. Tableaux statistiques descriptives exportables en CSV. Tableau de comparaison méthodes (kriging / RK / ML) avec RMSE / MAE / R² par paramètre et par domaine.

## Synthèse des points clés à retenir

Sur le **kriging 3D (domaine × profondeur)** : c'est la bonne direction scientifiquement, mais l'ordre d'exécution est critique. Il faut d'abord avoir des données propres (P0), puis un kriging 2D stratifié fonctionnel (P2), avant d'ajouter la dimension profondeur (P3). Faire P3 sur des données AMESSEFE corrompues produirait des horizons faux.

Sur les **graphiques dynamiques** : la séparation Plotly.js (figures légères, données JSON depuis l'API) vs Python via endpoint (variogrammes, cross-validation) est la bonne architecture pour le contexte Atlas. Les variogrammes en particulier ne peuvent pas être recalculés côté client — ils dépendent de PyKrige et d'un accès DB. L'endpoint `/ai/plots/variogram?run_id=X` génère le SVG une fois, le cache par `run_id`, et le re-sert instantanément — c'est idempotent et offline-friendly.

**Bonne pratique supplémentaire** : dès P2, ajoute un champ `sufficient_for_rk` (boolean) dans `atlas.ai_variograms`, calculé automatiquement comme `n_support_points >= 30 AND loo_rmse < sill * 0.35`. Le pipeline P4 peut alors interroger ce champ pour décider du niveau sans recalcul — et l'UI Admin peut afficher un indicateur "Éligible RK" par domaine/paramètre sans appel supplémentaire.
