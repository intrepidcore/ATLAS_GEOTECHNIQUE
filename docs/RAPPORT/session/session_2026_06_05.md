## 3. Incident #2 — Découverte de deux bases PostgreSQL (10h00)

### 3.1 Le problème invisible

Pendant 2 heures de monitoring, toutes les vérifications SQL montraient des résultats
vides ou obsolètes alors que les scripts Python confirmaient des insertions réussies :

```bash
# Ce que je voyais (faux négatif)
docker exec atlas-db psql -U atlas -d atlas_clean -c "
SELECT COUNT(*) FROM atlas.ai_interpolation_runs
WHERE created_at > now() - interval '5 hours';"
# → 0 rows

# Ce que les scripts Python loggaient
# "[OK] 29407 valeurs RK stockées (param=vbs_rk_h1)"
# "Run ID: 07f3bab3-7a91-4b8f-a38c-2ffb95dbfd0d"
```

### 3.2 Cause racine

Il existe **deux instances PostgreSQL distinctes** sur ce poste :

| Instance | Accès | Utilisé par |
|----------|-------|-------------|
| Container `atlas-db` | `docker exec atlas-db psql -U atlas` ou `127.0.0.1:5432` | — (base de développement isolée, peu à jour) |
| PostgreSQL 17 natif Windows | `127.0.0.1:5433` | **TOUS les scripts Python**, l'API Rust, le frontend |

La variable `DATABASE_URL=postgres://atlas:atlas@host.docker.internal:5433/atlas_clean`
dans `docker-compose.yml` pointe vers le PostgreSQL **natif Windows** (port 5433), pas
vers le container `atlas-db` (port 5432). Cette configuration — sans doute héritée d'une
migration architecturale — n'était pas documentée explicitement.

**Conséquence :** Pendant 2 heures, toutes mes vérifications SQL utilisaient la mauvaise
instance. Les données étaient correctement insérées sur port 5433, invisibles depuis
mes requêtes sur port 5432.

### 3.3 Correction du workflow de vérification

À partir de ce moment, toutes les requêtes SQL de vérification passent par :

```powershell
# CORRECT — pointe sur la vraie base de production
docker exec atlas-db psql "postgres://atlas:atlas@host.docker.internal:5433/atlas_clean" -c "..."

# INCORRECT — base container isolée (peu à jour)
docker exec atlas-db psql -U atlas -d atlas_clean -c "..."
```

**Impact sur la session :** Les 10 runs RK que je croyais absents étaient en réalité
présents sur port 5433. Le monitoring des calculs a pu reprendre correctement.

## 4. Bug #1 — MTGP ELBO=NaN (problème numérique critique)

### 4.1 Diagnostic depuis les logs

Les logs MTGP du run précédent (`/app/logs/mtgp_20260605_07*.log`) révélaient un
motif inquiétant : chaque itération d'optimisation produisait `ELBO final : nan`.

```
2026-06-05 07:35:22.395 | INFO  | GPflow jitter=1.0e-04 | rank=1 | max_iter=200
2026-06-05 07:35:22.520 | INFO  | Optimisation Adam GPU-native (max_iter=200)...
2026-06-05 07:35:30.888 | INFO  | ELBO final : nan
```

Ce pattern se répétait **toutes les 5–8 secondes** en boucle. Le GPU était sollicité
(87% VRAM) mais produisait des résultats mathématiquement invalides.

### 4.2 Analyse de la cause

Le modèle `VGP(SwitchedLikelihood, Coregion)` de GPflow est instable quand :

1. **Les coordonnées spatiales ne sont pas normalisées** : le kernel Matérn 3/2 opérait
   sur des lon/lat brutes (lon ≈ 0.1–1.8, lat ≈ 6.0–11.5). Sans normalisation, la
   matrice de covariance K(X,X) est très mal conditionnée → NaN dans la décomposition
   de Cholesky → NaN dans l'ELBO.

2. **Le jitter est trop faible** : `jitter=1e-4` est la valeur par défaut GPflow, conçue
   pour des données normalisées. Sur des données brutes, `1e-2` ou plus est nécessaire.

3. **Initialisation des paramètres Coregion** : La matrice W (coregionalisation) initialisée
   à zéro ou proche de zéro donne un noyau produit quasi-nul → `training_loss() → NaN`.

### 4.3 Fix implémenté dans `mtgp_geotechnique.py`

**a) Normalisation z-score dans `build_mtgp_data()`** :

```python
# Avant (bug)
X_p = np.column_stack([df_p["lon"].values, df_p["lat"].values, np.full(n, float(idx))])

# Après (fix)
lon_mean, lon_std = float(np.mean(lon_all)), float(np.std(lon_all)) + 1e-8
lat_mean, lat_std = float(np.mean(lat_all)), float(np.std(lat_all)) + 1e-8
lon_n = (df_p["lon"].values - lon_mean) / lon_std
lat_n = (df_p["lat"].values - lat_mean) / lat_std
X_p = np.column_stack([lon_n, lat_n, np.full(n, float(idx))])
```

Les scalers sont retournés par la fonction (`return X, Y, scalers`) pour être réappliqués
lors de la prédiction sur la grille (`predict_mtgp(model, df_grid, params, clamp, scalers=scalers)`).

**b) Normalisation des valeurs Y par paramètre** :

```python
y_scalers: Dict[str, Tuple[float, float]] = {}
for param in params:
    vals = df_train[param].dropna().values
    y_mean, y_std = float(np.mean(vals)), float(np.std(vals)) + 1e-8
    y_scalers[param] = (y_mean, y_std)
    y_norm = (df_p[param].values - y_mean) / y_std
    Y_p = np.column_stack([y_norm, np.full(n, float(idx))])
```

La dénormalisation est appliquée post-prédiction :
```python
if scalers is not None and param in scalers.get("y", {}):
    y_mean, y_std = scalers["y"][param]
    mean_col = mean_col * y_std + y_mean
    var_col  = var_col * (y_std ** 2)  # variance se scale au carré
```

**c) Jitter augmenté + retry NaN automatique** :

```python
def train_mtgp(..., jitter: float = 1e-2):  # était 1e-4
    ...
    # Détection NaN à iter=50 → retry avec jitter×10
    if math.isnan(elbo) or math.isinf(elbo):
        if not nan_retry_done and jitter < 0.5:
            new_jitter = jitter * 10.0
            log.warning("ELBO=NaN à iter=%d — retry avec jitter=%.2e", i, new_jitter)
            model = _build_model(new_jitter)
            nan_retry_done = True
            continue
```

**d) Initialisation correcte de la matrice W Coregion** :

```python
# Évite W≈0 → matrice de covariance nulle → NaN
kernel_coreg.W.assign(
    np.random.RandomState(42).randn(n_outputs, rank).astype(np.float64) * 0.1
)
kernel_coreg.kappa.assign(np.ones(n_outputs, dtype=np.float64) * 0.1)
```

## 5. Bug #2 — Séquençage MTGP : prédictions bloquées derrière LOO-CV (2h perdues)

### 5.1 Symptôme

Malgré un MTGP qui calculait correctement (ELBO convergeant), **aucune valeur n'apparaissait
en DB pendant 2 heures**. Le log montrait le pattern LOO-CV en boucle :

```
2026-06-05 09:25:32 | iter=0 ELBO=-0.0205
2026-06-05 09:25:44 | iter=50 ELBO=nan → retry jitter=1e-1
2026-06-05 09:26:12 | ELBO final : 0.000
... [répété 150 fois sur 2.5 heures]
```

### 5.2 Analyse du code

En lisant `run_mtgp()`, la séquence d'exécution était :

```python
# Ordre FAUTIF
1. load_training_data()          # OK
2. train_mtgp()                  # OK — modèle convergé
3. predict_mtgp()                # OK — 29 407 prédictions en mémoire
4. LOO-CV (30 iter × 5 params)  # ← BLOQUE ICI pendant ~150 min
5. INSERT run                    # ← Jamais atteint
6. store_mtgp_predictions()      # ← Jamais atteint
```

La LOO-CV (Leave-One-Out Cross-Validation) avec `n_iter_loo=30` réentraîne 30 modèles
GPflow par paramètre = 30×5 = 150 modèles × ~60s = **150 min de calcul** avant
d'écrire quoi que ce soit en base. Et ces mini-modèles LOO produisaient souvent ELBO=0
(solvable mais dégénéré avec peu de points), allongeant encore l'exécution.

### 5.3 Fix : stocker les prédictions AVANT la LOO-CV

```python
# Nouvel ordre (fix)
1. load_training_data()
2. train_mtgp()
3. predict_mtgp()
4. INSERT run avec status='running'     # ← Immédiat
5. store_mtgp_predictions()             # ← Données disponibles en ~15 min
6. LOO-CV (réduit à 10 iter)            # ← Évaluation post-écriture
7. UPDATE run → status='finished' + loo_rmse
```

Code de l'INSERT anticipé :
```python
cur.execute("""
    INSERT INTO atlas.ai_interpolation_runs
      (id, ..., status, metrics, started_at, ...)
    VALUES (%s, ..., 'running', %s::jsonb, now(), ...)
    """,
    (run_id, json_safe({
        "horizon_label": horizon_label,
        "loo_rmse": None,          # sera mis à jour après LOO-CV
        ...
    }), meta_base)
)
conn.commit()
# Écriture immédiate des prédictions
n_inserted = store_mtgp_predictions(conn, df_pred, params, horizon_label, run_id, clamp)
log.info("✓ %d valeurs MTGP insérées en DB avant LOO-CV", n_inserted)
```

Puis UPDATE après LOO-CV :
```python
cur2.execute("""
    UPDATE atlas.ai_interpolation_runs
    SET status = 'finished',
        finished_at = now(),
        metrics = metrics || %s::jsonb
    WHERE id = %s
    """,
    (json_safe({"loo_rmse": primary_loo, "loo_rmse_by_param": loo_by_param}), run_id)
)
```

### 5.4 Impact métier

Avec ce fix, les prédictions MTGP sont disponibles dans l'interface **~15 minutes après
le début du calcul** (temps d'entraînement GPU), pas après 2h30. La LOO-CV tourne en
arrière-plan et enrichit les métriques de qualité sans bloquer l'accès aux données.

## 6. Traçabilité unifiée — `utils/_run_traceability.py`

### 6.1 Problème observé

En interrogeant `ai_interpolation_runs` sur les runs du jour, trois patterns
d'incohérence ont été observés :

- **KED** : `model_version = 'v2'` (hardcodé), `started_at = finished_at = now()` (durée=0)
- **RK** : pas de `model_version`, `meta = {'source': '...', 'note': '...'}` minimal
- **BLUP** : `model_version = 'v1'` (hardcodé), pas de `meta`

Ces champs identiques pour tous les runs rendent impossible la comparaison entre
deux runs du même modèle avec des hyperparamètres différents.

### 6.2 Solution : utilitaire partagé

Création de `scripts/utils/_run_traceability.py` importé par KED, RK, BLUP et MTGP.

**Fonctions clés :**

```python
def build_version_tag(script_prefix: str, hyperparams: Optional[Dict] = None) -> str:
    """
    Retourne un tag reproductible : "<prefix>-<git_hash>-<hp_hash>"
    
    git_hash : 7 caractères du dernier commit (nogit si hors repo)
    hp_hash  : SHA1 des hyperparamètres — deux runs identiques auront le même hash,
               permettant d'identifier les re-runs sans changement de config
    """
    git = _git_hash()
    hp_str = str(sorted(hyperparams.items())) if hyperparams else ""
    hp_hash = hashlib.sha1(hp_str.encode()).hexdigest()[:8]
    return f"{script_prefix}-{git}-{hp_hash}"

def make_run_meta(script_name, hyperparams, metrics=None, t_start=None,
                  extra_modules=None) -> Dict:
    """
    Génère le dictionnaire meta complet pour ai_interpolation_runs.meta (jsonb).
    
    Contient :
    - git_hash, hp_hash          → reproductibilité
    - hyperparams                → exactement ce qui a tourné
    - software (python, sklearn, gpflow...) → environnement
    - started_at_utc, finished_at_utc, duration_sec → performance
    - metrics                    → qualité du run
    """
```

## 8. Bug #3 — `blup_fusion.rs` : erreur SQL "syntax error near VALUES"

### 8.1 Symptôme

L'appel `POST /ai/fusion/run` retournait `skipped=true` pour TOUTES les 12 combinaisons
(vbs/ip/wl/wp × h1/h2/h3) avec :
```json
"skip_reason": "insert_values vbs_fusion_h1: error returned from database: erreur de syntaxe sur ou près de « VALUES »"
```

Le même binaire avait produit 15 runs BLUP réussis à 08h45 ce matin. Donc la
régression était liée au changement de données, pas au code lui-même.

### 8.2 Investigation

**Hypothèse 1 (rejetée) : colonnes manquantes**
Le schema de `ai_interpolation_values` sur le host PostgreSQL confirmait `created_at NOT NULL`
absent du INSERT Rust. Mais l'erreur serait "violation de contrainte NOT NULL", pas
"syntax error near VALUES".

**Hypothèse 2 (rejetée) : paramètres > 65535**
500 rows × 7 colonnes = 3500 paramètres par batch. Largement sous la limite.

**Hypothèse 3 (retenue) : `push_values` sqlx 0.7 avec chunks**
La fonction `insert_fusion_values` utilisait `sqlx::QueryBuilder::push_values` qui
génère du SQL dynamique de la forme :
```sql
INSERT INTO ... (col1,...,col7) VALUES ($1,...,$7),($8,...,$14),...
```
Avec sqlx 0.7, le `push_values` peut produire du SQL invalide dans certains cas
impliquant des `Option<f64>` binds et des chunks non uniformes. Le comportement
avait peut-être changé avec un changement dans les données (les valeurs KED-HIER
ayant des variances non-NULL alors que les anciennes valeurs ked_pedological_prior
avaient des variances NULL pour certaines mailles).

### 8.3 Fix : remplacement par UNNEST arrays

Au lieu de générer du SQL dynamique multi-lignes, passage à une seule requête
paramétrique avec `unnest()` :

```rust
// Avant (buggy avec push_values)
for chunk in rows.chunks(500) {
    let mut builder = sqlx::QueryBuilder::new(
        "INSERT INTO atlas.ai_interpolation_values \
         (id, maille_id, parameter_id, value, variance, method, run_id) VALUES ",
    );
    builder.push_values(chunk, |mut b, (maille_id, z, sigma2)| {
        b.push_bind(Uuid::new_v4()).push_bind(maille_id)...
    });
    builder.build().execute(pool).await?;
}

// Après (UNNEST — robuste et plus rapide)
let ids: Vec<Uuid>              = rows.iter().map(|_| Uuid::new_v4()).collect();
let maille_ids: Vec<Uuid>       = rows.iter().map(|(m, _, _)| *m).collect();
let values: Vec<f64>            = rows.iter().map(|(_, z, _)| *z).collect();
let variances: Vec<Option<f64>> = rows.iter().map(|(_, _, v)| *v).collect();

sqlx::query(r#"
    INSERT INTO atlas.ai_interpolation_values
      (id, maille_id, parameter_id, value, variance, method, run_id, created_at)
    SELECT
      unnest($1::uuid[]), unnest($2::uuid[]),
      $3::text,
      unnest($4::float8[]), unnest($5::float8[]),
      $6::text, $7::uuid, now()
"#)
.bind(&ids).bind(&maille_ids)
.bind(fusion_param_id)
.bind(&values).bind(&variances)
.bind(FUSION_METHOD).bind(run_id)
.execute(pool).await?;
```

**Avantages de l'approche UNNEST :**
- Une seule aller-retour réseau vers PostgreSQL (vs 59 pour 29 407 lignes)
- Pas de génération SQL dynamique → pas de risque de malformation
- PostgreSQL optimise mieux un seul INSERT massif qu'une boucle de 500

Le fix est dans le source. Le rebuild attend une connexion WiFi stable (l'image
`rust:1.86` n'est pas en cache local — le build échoue avec TLS timeout sur les
couches manquantes).

**Workaround actuel :** Utiliser `ked_rk_fusion.py` directement, qui fonctionne
correctement et utilise bien `ked_hierarchical_5levels` en priorité.

## 9. Hiérarchie KED — Divergence article vs implémentation

### 9.1 Question posée par le collaborateur

Le collaborateur citait l'Équation (4) de l'article qui décrirait l'ordre :
`RGA → Zone géomorphologique → Pédologie → Géologie → Moyenne nationale`

### 9.2 Vérification dans le code source

Lecture de `create_contexte_geologique.sql` :

```sql
CONCAT_WS('|',
    COALESCE(z.nom, 'NAT'),                    -- Niveau 1 : Zone (géomorphologique)
    LEFT(COALESCE(up.type_sol, 'INC'), 4),     -- Niveau 2 : Pédologie
    COALESCE(rg.niveau_risque, 'INC'),         -- Niveau 3 : Risque RGA
    LEFT(COALESCE(ug.type_sols, 'INC'), 6)     -- Niveau 4 : Géologie nationale
) AS contexte_complet
```

Et dans `compute_hierarchical_prior()` (`run_ked_vbs_ip_wl_wp_horizons.py`) :
```python
# Repli niveau 1 : ZONE|PEDO|RISQUE|GEO   (min_pts=5)
# Repli niveau 2 : ZONE|PEDO              (RGA abandonné à ce niveau !)
# Repli niveau 3 : PEDO seule
# Repli niveau 4 : Moyenne globale
```

### 9.3 Conclusion et documentation

Le code implémente : **Zone → Pédologie → RGA → Géologie → Nationale**
L'article décrit : **RGA → Zone → Pédologie → Géologie → Nationale**

Ces deux ordres sont différents. Plus important encore : dans le code, **RGA est
abandonné dès le niveau de repli 2** (seuls ZONE|PEDO survivent), alors que l'article
le traite comme le discriminant principal.

Conséquence pratique : pour les zones sans assez de sondages avec le même niveau RGA
dans la même ZONE, le modèle ignore RGA et se replie sur la pédologie. Ce choix
d'implémentation est peut-être justifié empiriquement (les zones géomorphologiques
comme la Dépression de la Lama sont de meilleurs prédicteurs au Togo que le RGA),
mais il devra être documenté dans l'article.

**Action documentée dans `A_LIRE_1.md` section 9 + `AUDIT_GEOCODAGE_CRITIQUE_2026-06-04.md`.**

### 10.3 Stratégie pip cache pour les sessions futures

Le cache pip de 2.3 Go (tensorflow, gpflow, sklearn, pandas) est dans `/root/.cache/pip`
à l'intérieur du container. Il disparaît à chaque recréation du container.

**Solution à long terme implémentée :**

1. **Baking dans l'image** : Le Dockerfile ajoute désormais le `pip install` dans la
   stage runtime avec `--mount=type=cache` BuildKit :

```dockerfile
FROM debian:bookworm-slim
...
RUN --mount=type=cache,target=/root/.cache/pip \
    pip3 install --break-system-packages \
    pandas==2.0.3 scikit-learn==1.3.2 \
    'tensorflow[and-cuda]>=2.15,<2.16' gpflow==2.10.1
```

   Le `--mount=type=cache` préserve le cache pip entre les builds Docker sans
   l'inclure dans les couches de l'image finale. Après le premier build (~2 Go
   téléchargés), les suivants utilisent le cache BuildKit (~30 secondes).

2. **Volume persistant** dans `docker-compose.yml` :

```yaml
services:
  api-geo:
    volumes:
      - ./exports:/data/exports
      - ./scripts:/opt/atlas/scripts:ro
      - ml-pip-cache:/root/.cache/pip    # ← nouveau

volumes:
  ml-pip-cache:    # persiste entre les recreations du container
```

3. **Script de restauration** : `scripts/install_ml_deps_docker.sh` documenté
   avec la commande de restauration depuis backup.
