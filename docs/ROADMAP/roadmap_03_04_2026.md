Le plan est bien structuré et couvre les trois axes essentiels. Voici mon analyse critique et le plan complet amélioré.

## Ce que le plan fait bien

Les trois axes (thématique, drawer, DB Manager) sont les bons. La séparation entre "brancher les données" et "corriger l'UX" est claire. Le diagramme Mermaid montre correctement le flux de données. La notion de "définition de branché correctement" avec des critères vérifiables est une bonne pratique.

## Ce qui manque ou mérite correction

**Manque 1 — Le badge `source_type` n'est pas dans le plan.** C'est pourtant le point le plus important pour la défendabilité scientifique : un ingénieur qui voit `IP = 28%` doit savoir si c'est une mesure réelle ou une interpolation. Sans ce badge, l'UI expose des données sans contexte de confiance.

**Manque 2 — Le sélecteur d'horizon H1/H2/H3 n'est pas traité.** Le plan ajoute les paramètres `*_ked_h1/h2/h3` comme entrées distinctes dans le catalogue. C'est une approche qui fonctionne mais qui n'est pas la bonne UX — l'utilisateur devrait choisir un paramètre (`VBS`) puis un horizon (`H1/H2/H3`) via un sélecteur dédié, pas chercher `vbs_ked_h2` dans une liste de 40 entrées.

**Manque 3 — Le plan ne traite pas la carte de densité de données.** C'est la couche "fiabilité" qui montre combien de sondages réels existent à proximité de chaque maille. Sans elle, les cartes KED donnent une fausse impression de précision uniforme sur tout le territoire.

**Manque 4 — La migration vers `atlas.ai_job_queue` dans `ai_jobs.rs` est mentionnée mais sous-spécifiée.** La rétrocompatibilité avec les clients qui lisent encore `atlas.ai_training_jobs` n'est pas traitée.

## Les 5 décisions architecturales importantes à retenir

**Décision 1 — Paramètre + horizon séparés dans le catalogue UI**

Le plan original crée 40 entrées dans `THEMATIC_PARAMETERS` (7 params × 3 horizons × 2 types de granulo...). C'est ingérable pour l'utilisateur et pour la maintenance. L'approche correcte est 7 paramètres avec un champ `horizons: ['H1','H2','H3']`, et le sélecteur H1/H2/H3 est généré automatiquement. Le `parameter_id` envoyé à l'API est construit dynamiquement : `vbs_ked_h2` vient de `vbs` + `H2`.

**Décision 2 — Le badge source_type est non négociable**

C'est le point le plus important pour la crédibilité scientifique d'Atlas. Sans ce badge, l'UI affiche des valeurs sans contexte — c'est une plateforme qui génère de la confiance aveugle dans des données interpolées. La norme dans toutes les plateformes géotechniques sérieuses (BRGM InfoTerre, USGS) est d'indiquer clairement la provenance de chaque valeur.

**Décision 3 — Séparer CI niveau 1 et niveau 2**

Relancer les runners KED en CI de routine serait une erreur coûteuse. Le niveau 1 vérifie la structure (compilation, tests unitaires, migrations), le niveau 2 vérifie les données existantes sans recalculer.

**Décision 4 — La carte de densité de données complète les cartes KED**

Sans elle, les cartes KED donnent une fausse impression de précision uniforme. Une zone avec 0 sondage à 100km et une zone avec 15 sondages à 5km ont la même apparence visuelle — ce qui est trompeur pour un ingénieur qui dimensionne des fondations.

**Décision 5 — Rétrocompatibilité ai_training_jobs**

Ne pas supprimer `atlas.ai_training_jobs` en une seule migration. Ajouter un flag `source_table` dans la réponse JSON pour que l'UI sache quelle table est lue. La suppression se fait dans une migration ultérieure, après validation que rien ne lit encore l'ancienne table.

**Bonne pratique supplémentaire :** avant de livrer l'AXE 1 (panneau thématique), produis un test de cohérence cross-langage automatisé — un script Python qui lit `THEMATIC_PARAMETERS` depuis le fichier TypeScript (ou depuis le catalog DB) et vérifie que chaque `parameter_id` correspond à une entrée valide dans l'enum Rust `ThematicParameter`. Ce test prend 30 minutes à écrire et élimine définitivement la classe de bugs "paramètre dans l'UI mais absent de l'API" qui a causé plusieurs iterations dans les sessions précédentes.
